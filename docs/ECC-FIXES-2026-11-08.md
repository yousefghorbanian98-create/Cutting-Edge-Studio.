## C2 — `h264_nvenc` falsely reported on GPU-less machines (HIGH)

The worst finding, and a genuine correctness defect that 565 passing tests missed.

`detect_h264_encoder()` parsed `ffmpeg -hide_banner -encoders` and returned the first
allowed name. **Listing is not availability**: an FFmpeg build advertises `h264_nvenc`
whenever it was compiled with NVENC support, regardless of whether a GPU or
`libcuda.so.1` exists at runtime. On this machine the API cheerfully returned:

```json
{"encoder":"h264_nvenc","hardware":true}
```

with no NVIDIA device present. The unit tests passed because `tests/fixtures.py:45`
feeds a *synthetic* `-encoders` string containing the NVENC line — the fixture asserted
the bug.

**Fix.** The encoder is now proven by opening it, not by reading a list:

- `ffmpeg.py` gained `candidate_h264_encoders()` and `encoder_smoke_command()`, which
  builds a one-frame null-output probe. It stays a pure function, preserving the
  module's "never shells out" contract — execution remains the service layer's job.
- `service.detect_h264_encoder()` walks candidates in preference order, keeps the first
  whose probe exits 0, and falls back otherwise. The verdict (including `None`) is
  cached on the app-level `MediaService` singleton, so the probe runs once per process.

Rejections are now loud rather than silent:

```
media.encoder.smoke_failed        encoder=h264_nvenc  "Cannot load libcuda.so.1"
media.encoder.listed_but_unusable encoder=h264_nvenc
media.encoder.selected            encoder=libopenh264
```

**Verified live** against the running sidecar:

```json
{"encoder":"libopenh264","hardware":false,"note":"software/openh264 path"}
```

A second request produced no further probes, confirming the cache. Four regression
tests cover the smoke-command shape, the listed-but-unopenable fallback, caching, and
the all-fail → `None` path.

> The previous review's "no correctness defect found" conclusion is **superseded** by
> this finding.

## C1 — the Post feature was built twice and wired zero times (HIGH)

Twelve working `/api/v1/post/*` endpoints and 841 lines of services were unreachable:
`PostPanel` rendered entirely from a hardcoded table whose own comment admitted it
*"Mirrors backend PRESETS"*, with nothing enforcing agreement.

**Fix.** `api.ts` gained `postPresets()` / `postLayouts()`; `postStore` gained
`hydrateFromBackend()`; `PostPanel` calls it from an aborting `useEffect`. The backend
now owns the geometry; the UI keeps only i18n `labelKey`s, mapped by preset id.

The bundled table is **retained as an offline fallback** — this is an offline-first
desktop app, so an unreachable sidecar must not empty the panel. It is no longer a
second source of truth, because C5 below makes divergence a build failure.

**Verified live** — the panel now issues real calls on mount:

```
200 GET /post/presets
200 GET /post/layouts
```

(previously: zero). All five presets render with Persian labels intact; zero page
errors. Screenshot: `evidence/ecc-fixes-2026-11-08/post-panel-wired-to-backend.png`.

## C5 — nothing stopped the two preset tables drifting (MEDIUM)

New `backend/tests/test_post_contract.py` (8 tests) parses the frontend store and
compares it to `PRESETS`: exact id/width/height/max-seconds equality, every backend
preset reachable from the UI, comparison layouts matching `replay.LAYOUTS`, and a
regression guard asserting the panel still *calls* the endpoint.

**Proven to actually fail**: changing one digit (`shorts.maxSeconds` 60 → 59) produced

```
AssertionError: post preset tables drifted between frontend fallback and backend.
```

The test also immediately caught the F3 refactor moving `postStore.ts` — a guard that
earns its keep on day one.

## F1 — `src-tauri/Cargo.lock` is not committed (HIGH)

**This cannot be fixed in this sandbox and has not been faked.** There is no Rust
toolchain here and `crates.io` / `static.rust-lang.org` are outside the network
allowlist. Hand-resolving ~300 transitive crates with feature unification would produce
a *wrong* lockfile — worse than none.

Instead it is now **impossible to ignore**. The new `rust` CI job generates a throwaway
lockfile so clippy and tests still produce signal, then fails the job at the end with
the exact remedy:

```
cd src-tauri && cargo generate-lockfile && git add Cargo.lock
```

Expect this one check to be red until a developer with crates.io access commits the
lockfile. That red is the finding, correctly surfaced.

## F2 — Rust was never compiled on pull requests (MEDIUM)

`src-tauri` was built only by the Windows installer job, which does not run on PRs, so
its unit tests had never executed in CI. Added a `rust` job (Ubuntu, Tauri v2 system
deps) running `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, and
`cargo test`.

Checked before committing: the crate has no Windows-only dependencies and no
`cfg(windows)` in `src/`, so a Linux build is sound. The pinned action SHAs were
verified against the GitHub API and are **the same pins the existing installer job
already uses** — `dtolnay/rust-toolchain@b725eda` (head of `stable`) and
`Swatinem/rust-cache@d1527c8` (= tag `v2.9.3`). No SHA was invented.

Cannot be executed locally (no `cargo`); the YAML was validated by parsing.

# Follow-up — 2026-11-08 (themes, installer, dead code)

## Theme switching — works, with one real bug found and fixed

All three themes were exercised in a live browser, reading the computed custom
properties after each switch:

| Theme | `data-theme` | `--bg-primary` | `--accent-primary` |
|---|---|---|---|
| pro | `pro` | `#0a0a0b` | `#ff6b35` orange |
| glass | `glass` | `#0f0a1e` | `#a855f7` purple |
| minimal | `minimal` | `#09090b` | `#5b8def` blue |

3/3 distinct renders, zero page errors. Mechanism verified sound: `setTheme` writes a
single `data-theme` attribute, `:root, :root[data-theme='pro']` makes the default safe
before any switch, and workspace restore routes through `setTheme` rather than setting
state directly, so a restored theme is actually applied.

**Bug found:** the three theme blocks did not declare the same variables. `glass`
defined `--glass-bg` and `--glass-blur`; `pro` and `minimal` did not. The only consumer,
`.glass-panel`, used them without fallbacks:

```css
.glass-panel {
  background: var(--glass-bg);
  backdrop-filter: blur(var(--glass-blur));
}
```

Outside the glass theme both resolve to nothing, so the background falls back to
transparent and the whole `backdrop-filter` declaration is dropped as invalid, leaving a
bare border. `.glass-panel` turned out to have **zero consumers** while still shipping in
the production CSS bundle, so it was deleted along with its two orphan variables.

Three regression tests now pin the contract: every theme declares exactly the same
variable set, and no rule may reference a custom property no theme defines. Verified by
injecting a glass-only variable and watching the suite fail.

## Windows installer — staged, prerequisite-aware

Implemented as Tauri's supported `installerHooks` extension point. Full write-up in
[`INSTALLER-DESIGN.md`](./INSTALLER-DESIGN.md).

Five stages reported into one progress view: system requirements (x64, Windows build,
**AVX2**, RAM, disk) → install the bundled Visual C++ runtime if absent → re-verify it
registered → Tauri installs the app → verify the binaries, UI and frozen Python runtime
landed.

Two design decisions worth stating:

* **No downloads.** The usual "bootstrapper fetches the redist" pattern would break the
  product's offline lock, so the redistributable is SHA-256 pinned in `pins.json`,
  fetched on the build machine, and embedded. A test blocks `inetc::`, `NSISdl::` and
  bare URLs from the hook script.
* **No overlap with Tauri.** WebView2 installation, file copying, shortcuts and the
  uninstaller stay with the generated template; the hooks only read WebView2 state to
  report it. A test asserts the hook never creates shortcuts or writes an uninstaller.

**Not yet executed on Windows.** `makensis` is unavailable in this sandbox, so the 15
contract tests are a pre-filter; the authoritative check is the existing `installer`
job on `windows-latest`, which compiles the bundle and installs it.
